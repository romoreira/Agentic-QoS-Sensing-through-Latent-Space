# TRex Four-Slice Noise Toolkit

Standalone toolkit to audit four GTP-U slice streams on a single TRex uplink before connecting the traffic source to the DQN environment.

The design intentionally follows the working profile shape:

- one physical TRex TX port
- one GTP-U stream per slice
- TEIDs 1, 11, 21 and 31
- Gold, Silver and Bronze are the future DQN-controlled slices
- Noise is a fourth background slice used to perturb the shared uplink/N6 path
- no port-per-slice assumption

## Slice map

| Slice | TEID | UE IP | UDP source port | PG ID | Role |
|---|---:|---|---:|---:|---|
| Gold | 1 | 10.250.0.1 | 10001 | 1 | DQN-controlled later |
| Silver | 11 | 10.250.0.2 | 10011 | 11 | DQN-controlled later |
| Bronze | 21 | 10.250.0.3 | 10021 | 21 | DQN-controlled later |
| Noise | 31 | 10.250.0.4 | 10031 | 31 | background pressure |

Packet shape:

```text
Ether / outer IP gNB -> UPF N3 / UDP 2152 / GTP-U TEID / inner IP UE -> DN / UDP / payload
```

Defaults:

```text
GNB_IP    192.168.70.2
UPF_N3_IP 192.168.70.1
DN_IP     192.168.80.2
payload   128 bytes
```

## Traffic model

Each slice rate is generated by:

```text
offered_i(t) = mean_i(regime) + amplitude_i(regime) * [sinusoids_i(t) + AR1_i(t)] + burst_i(t)
```

The fourth slice, Noise, is not fixed traffic. It has higher variance and stronger regime amplification:

```text
base mean  30 Mbps
base std   20 Mbps
phase      pi/3
frequencies 0.05, 0.13, 0.27 Hz
AR(1) rho  0.80
burst rate 0.05 events/s
```

Regimes change every 8 to 25 seconds. Noise receives mean multipliers:

```text
1.00, 1.40, 0.80, 1.60
```

and amplitude multipliers:

```text
1.00, 1.50, 0.70, 1.70
```

This creates a fourth hidden pressure source for the DQN experiment later, while allowing you to audit the generated curves now.

## 2. Run the static profile in TRex, fixed rates

This is the closest static version of the profile you already validated:

```bash
cd /opt/trex/v3.08
sudo ./t-rex-64 -i
```

In another terminal:

```bash
export PYTHONPATH=/opt/trex/v3.08/automation/trex_control_plane/interactive:$PYTHONPATH
cd /path/to/trex_4slice_noise_toolkit
python3 - <<'PY'
from trex_stl_lib.api import STLClient
from profiles.exp4_4slice_single_uplink_profile import register

c = STLClient(server='127.0.0.1')
c.connect()
c.acquire(ports=[0], force=True)
c.reset(ports=[0])
c.add_streams(register().get_streams(), ports=[0])
c.start(ports=[0], duration=60)
print('started four streams on one uplink port 0')
c.disconnect()
PY
```

This runs Gold, Silver, Bronze and Noise continuously on port 0. It is useful to verify BESS receives all four TEIDs.

## 3. Run the dynamic traffic audit on TRex

The dynamic runner changes the four stream rates according to the traffic model and logs target curves to CSV and TensorBoard.

```bash
export PYTHONPATH=/opt/trex/v3.08/automation/trex_control_plane/interactive:$PYTHONPATH
python3 scripts/run_trex_dynamic_4slice.py \
  --host 127.0.0.1 \
  --port 0 \
  --duration 180 \
  --dt 1.0 \
  --force \
  --csv runs/trex_dynamic_targets.csv \
  --jsonl runs/trex_dynamic_targets.jsonl \
  --tb runs/tensorboard/trex_dynamic
```

For a dry run without TRex:

```bash
python3 scripts/run_trex_dynamic_4slice.py \
  --plan-only \
  --duration 180 \
  --dt 1.0 \
  --csv runs/trex_dynamic_targets.csv \
  --tb runs/tensorboard/trex_dynamic
```

Important: the dynamic runner uses conservative per-window reloads. It is for audit and curve validation. The final closed-loop experiment should later use a cleaner TRex source or keep TRex fixed and let BESS/QER enforcement be the variable.

## 5. Prepare BESS/PFCP for four slices

The BESS side needs one session/rule set for each TEID:

```text
TEID 1   UE 10.250.0.1  Gold
TEID 11  UE 10.250.0.2  Silver
TEID 21  UE 10.250.0.3  Bronze
TEID 31  UE 10.250.0.4  Noise
```

Start with:

```bash
bash bess/check_bess_4slices.sh
```

This collects:

```text
bessctl show pipeline
bessctl show port n3
bessctl show port n6
pfcpctl service session list
```

Edit `bess/four_slices.env` if your BESS port names are not `n3` and `n6`.

For continuous BESS-side raw metric collection:

```bash
source bess/four_slices.env
python3 scripts/audit_bess_stats.py \
  --duration 180 \
  --dt 1.0 \
  --n3-port "$N3_PORT_NAME" \
  --n6-port "$N6_PORT_NAME" \
  --csv runs/bess_stats.csv \
  --raw-dir runs/bess_raw \
  --tb runs/tensorboard/bess_stats
```

If you know the BESS module names for QER/meter modules, add them:

```bash
python3 scripts/audit_bess_stats.py \
  --module qer_gold \
  --module qer_silver \
  --module qer_bronze \
  --module qer_noise
```

## Expected audit workflow

1. Generate plan only and inspect the four curves in TensorBoard.
2. Run the static profile and confirm BESS sees TEIDs 1, 11, 21 and 31.
3. Run the dynamic TRex audit and inspect target curves.
4. Run TRex and BESS stat collectors in parallel.
5. Once BESS mappings are confirmed, connect these metrics to the DQN environment.

## Real telemetry probe

This probe runs on the TRex host and collects one synchronized row per window.
It uses TRex PG-ID counters for per-slice TX/RX/loss and UPF Prometheus for
N6 aggregate throughput. The RX/N6 port defaults to `--rx-port 1` and is put
in service mode automatically, matching the manual TRex console command
`service --port 1`.

```bash
export PYTHONPATH=/opt/trex/v3.08/automation/trex_control_plane/interactive:$PYTHONPATH

python3 scripts/real_telemetry_probe.py \
  --host 127.0.0.1 \
  --port 0 \
  --rx-port 1 \
  --duration 60 \
  --dt 1.0 \
  --upf-metrics-url http://192.168.90.1:8080/metrics \
  --force \
  --csv runs/real_telemetry_probe_60s.csv \
  --jsonl runs/real_telemetry_probe_60s.jsonl \
  --tb runs/tensorboard/real_telemetry_probe_60s
```

A valid run should have `pfcp_sessions=4`, positive `n6_total_mbps`, and positive
`rx_*_mbps` for the controlled slices. If `n6_total_mbps` is positive but all
`rx_*_mbps` are zero, check that TRex is running in software latency mode and
that `--rx-port 1` is correct for the N6 receive port.

## v3 note

real_telemetry_probe.py now reads TRex PG-ID dictionaries with integer keys and prefers *_total counters over per-port *_0 keys, fixing RX per-slice values for STLFlowLatencyStats.

## Traffic model modes

The toolkit now supports two traffic generators.

### stochastic

Default mode. This is the original AR(1) + regime + lognormal burst model. It is useful to stress the controller, but the curves can look noisy in TensorBoard.

```bash
--traffic-model stochastic
```

### sine_abrupt

Curriculum/audit mode. Gold, Silver and Bronze are smooth non-synchronized sinusoidal loads. Noise is the fourth slice and changes abruptly between quiet and active states. This mode is easier to inspect visually and is recommended before plugging the real telemetry into DQN.

```bash
--traffic-model sine_abrupt
```

Example, one hour with real telemetry:

```bash
python3 scripts/real_telemetry_probe.py \
  --host 127.0.0.1 \
  --port 0 \
  --rx-port 1 \
  --duration 3600 \
  --dt 1.0 \
  --traffic-model sine_abrupt \
  --upf-metrics-url http://192.168.90.1:8080/metrics \
  --force \
  --csv runs/hour_sine_abrupt/real_telemetry_probe_1h.csv \
  --jsonl runs/hour_sine_abrupt/real_telemetry_probe_1h.jsonl \
  --tb runs/tensorboard/real_telemetry_probe_1h_sine_abrupt
```

Example, plan only, no TRex:

```bash
python3 scripts/preview_traffic_model.py \
  --traffic-model sine_abrupt \
  --duration 3600 \
  --dt 1.0 \
  --csv runs/hour_sine_abrupt/traffic_plan_1h.csv \
  --tb runs/tensorboard/traffic_plan_1h_sine_abrupt
```
