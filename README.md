# 🧠 DQN Proxy Control for Gold Slice Protection over BESS UPF and TRex

This README documents the current experiment state, the bring-up sequence, the initial PFCP session setup, the TRex four-slice traffic generator, and the online DQN proxy training procedure.

The goal is to make the experiment reproducible from a clean repository checkout by someone who does not know the previous debugging history.

---

## ✅ What this experiment does

This experiment trains an online DQN controller to protect a critical **Gold** slice over a shared uplink.

The controller changes the application-level MBR of non-critical slices through real PFCP session modification commands. Traffic is generated by TRex and forwarded through the BESS UPF.

The controller does **not** rely on RX per-slice PGID counters, because TRex RX PGID attribution does not survive the UPF GTP-U decapsulation path. Instead, the experiment uses a **control-plane proxy** based on the offered traffic and the MBR currently installed in the UPF.

The proxy is used only for reward and diagnostics. The actual packet path still goes through TRex, GTP-U, BESS UPF, QER metering, and N6 forwarding.

What `setup_pfcpsim.sh` does

```bash

sudo docker run --rm -d --network host \
  --name pfcpsim \
  pfcpsim:patched \
  -p 12345 \
  --interface enp9s0

sudo docker exec pfcpsim pfcpctl -s localhost:12345 service configure \
  --n3-addr 192.168.70.1 \
  --remote-peer-addr 192.168.90.1

sudo docker exec pfcpsim pfcpctl -s localhost:12345 service associate

sudo docker exec pfcpsim pfcpctl -s localhost:12345 session create \
  --count 4 \
  --baseID 1 \
  --ue-pool 10.250.0.0/24 \
  --gnb-addr 192.168.70.2 \
  --app-filter "udp:any:any:allow:100" \
  --session-mbr-uplink   1000000,1000000,1000000,1000000 \
  --session-mbr-downlink 1000000,1000000,1000000,1000000 \
  --app-mbr-uplink       200000,100000,50000,50000 \
  --app-mbr-downlink     200000,100000,50000,50000
```

Important note

`setup_pfcpsim.sh` is for **initial provisioning only**. It removes and recreates the `pfcpsim` container and creates the PFCP sessions from scratch. It must not be used as the online DQN action mechanism.

The online action mechanism is

```bash
sudo docker exec pfcpsim pfcpctl -s localhost:12345 session modify ...
```

This modifies existing sessions in place.

## 🧪 What we debugged and why proxy mode is used

TRex TX by PGID works.

TRex RX physical counters work.

TRex RX by PGID does **not** work after UPF decapsulation.

The reason is that TRex sends GTP-U packets on N3, but after the UPF decapsulates the packet, N6 receives only the inner UE-to-DN packet.

Example packet observed on TRex RX port 1

```text
10.250.0.3.10021 > 192.168.80.2.5555
10.250.0.2.10011 > 192.168.80.2.5555
10.250.0.1.10001 > 192.168.80.2.5555
10.250.0.4.10031 > 192.168.80.2.5555
```

Therefore, `stats -s` and `stats -l` can count TX by PGID, but cannot assign RX packets back to the same PGID after decapsulation.

Conclusion

```text
TRex PGID is valid for TX offered load per slice.
TRex PGID is not valid for RX per slice after the BESS UPF decapsulates GTP-U.
```

For this reason, the current experiment uses a control-plane proxy.

## 🧮 Proxy model

The proxy estimates whether Gold had enough uplink capacity after the MBR-limited non-critical slices and hidden burst consumed part of the shared link.

The shared uplink capacity is currently

```text
200 Mbps
```

The traffic after MBR is

```python
after_mbr_gold   = min(offered_gold,   mbr_gold)
after_mbr_silver = min(offered_silver, mbr_silver)
after_mbr_bronze = min(offered_bronze, mbr_bronze)
after_mbr_hidden = min(hidden_burst,   mbr_noise)
```

Available capacity for Gold is

```python
available_for_gold = uplink_capacity - after_mbr_silver - after_mbr_bronze - after_mbr_hidden
```

Gold shortage is

```python
gold_shortage = max(0, after_mbr_gold - available_for_gold)
```

This is the main metric minimized by the DQN.

## 🎮 DQN action space

The online DQN chooses one of the following actions.

| Action ID | Action name | Gold MBR | Silver MBR | Bronze MBR | Meaning |
|---:|---|---:|---:|---:|---|
| 0 | `nominal` | 200000 | 100000 | 50000 | Initial nominal allocation |
| 1 | `cut_non_gold_light` | 200000 | 70000 | 30000 | Light cut on non-critical slices |
| 2 | `cut_non_gold_medium` | 200000 | 40000 | 15000 | Medium cut on non-critical slices |
| 3 | `cut_non_gold_strong` | 200000 | 15000 | 5000 | Strong cut on non-critical slices |
| 4 | `reserve_gold_light` | 220000 | 60000 | 20000 | Slight Gold reservation |
| 5 | `reserve_gold_strong` | 240000 | 15000 | 5000 | Strong Gold reservation |
| 6 | `restore_silver` | 220000 | 100000 | 10000 | Restore Silver, keep Bronze low |
| 7 | `restore_bronze` | 220000 | 30000 | 50000 | Restore Bronze, keep Silver low |

Noise is currently fixed at 50 Mbps MBR.

## 🎯 Reward function

The reward is a negative-cost objective.

The best behavior is reward close to zero.

A very negative reward means the policy caused Gold shortage or excessive poor allocation.

Current reward structure

```python
reward = (
    - 20.0 * gold_shortage
    - 0.35 * silver_mbr_drop
    - 0.20 * bronze_mbr_drop
    - 0.50 * action_change_penalty
    - 0.50 * non_gold_starvation_penalty
    +  5.0 * healthy_uplink_utilization
)
```

Interpretation

```text
reward very negative       bad policy
reward less negative       better policy
reward near zero           Gold protected with low penalty
```

This is normal for a cost-minimization RL setup. For presentation, a positive protection score can be computed later from the CSV.

```python
gold_protection_score = 1.0 - gold_shortage_mbps / offered_gold_mbps
```

    c.acquire(ports=[0, 1], force=True)

This can happen because TRex uses DPDK/PMD and packets do not pass through the Linux kernel path.

Use TRex counters or TRex capture instead.

### TRex capture on RX gets no packets

Enable service mode on RX port 1 before capture.

```text
service --port 1
```

## 📝 Short experiment summary

This experiment implements an online DQN controller for adaptive QoS enforcement in a BESS-based UPF. TRex generates four GTP-U slices, Gold, Silver, Bronze, and Noise. The Gold slice is critical and varies between approximately 100 and 200 Mbps. Silver and Bronze generate competing traffic, while Noise creates hidden burst pressure.

Because TRex RX PGID counters cannot attribute packets after GTP-U decapsulation, the controller uses a proxy based on offered load, active MBRs, and shared uplink capacity. The DQN applies real PFCP `session modify` commands to change slice MBRs online. The first validated 900 s run showed decreasing training loss, improved reward, and reduced Gold shortage, indicating that the controller learned to reserve uplink capacity for the critical Gold slice.
