# 🧠 DQN Proxy Control for Gold Slice Protection over BESS UPF and TRex

This README documents the current experiment state, the bring-up sequence, the initial PFCP session setup, the TRex four-slice traffic generator, and the online DQN proxy training procedure.

The goal is to make the experiment reproducible from a clean repository checkout by someone who does not know the previous debugging history.

---

## ✅ What this experiment does

This experiment trains an online DQN controller to protect a critical **Gold** slice over a shared uplink.

The controller changes the application-level MBR of non-critical slices through real PFCP session modification commands. Traffic is generated by TRex and forwarded through the BESS UPF.

The controller does **not** rely on RX per-slice PGID counters, because TRex RX PGID attribution does not survive the UPF GTP-U decapsulation path. Instead, the experiment uses a **control-plane proxy** based on the offered traffic and the MBR currently installed in the UPF.

The proxy is used only for reward and diagnostics. The actual packet path still goes through TRex, GTP-U, BESS UPF, QER metering, and N6 forwarding.

```bash

sudo docker run --rm -d --network host \
  --name pfcpsim \

  --n3-addr 192.168.70.1 \
  --remote-peer-addr 192.168.90.1

sudo docker exec pfcpsim pfcpctl -s localhost:12345 service associate

sudo docker exec pfcpsim pfcpctl -s localhost:12345 session create \
  --count 4 \
  --baseID 1 \
  --ue-pool 10.250.0.0/24 \
  --gnb-addr 192.168.70.2 \
  --app-filter "udp:any:any:allow:100" \
  --session-mbr-uplink   1000000,1000000,1000000,1000000 \
  --session-mbr-downlink 1000000,1000000,1000000,1000000 \
  --app-mbr-uplink       200000,100000,50000,50000 \
  --app-mbr-downlink     200000,100000,50000,50000
```

Important note

`setup_pfcpsim.sh` is for **initial provisioning only**. It removes and recreates the `pfcpsim` container and creates the PFCP sessions from scratch. It must not be used as the online DQN action mechanism.

The online action mechanism is

```bash
sudo docker exec pfcpsim pfcpctl -s localhost:12345 session modify ...
```

This modifies existing sessions in place.

## 🧪 What we debugged and why proxy mode is used

TRex TX by PGID works.

TRex RX physical counters work.

TRex RX by PGID does **not** work after UPF decapsulation.

The reason is that TRex sends GTP-U packets on N3, but after the UPF decapsulates the packet, N6 receives only the inner UE-to-DN packet.

Example packet observed on TRex RX port 1

```text
10.250.0.3.10021 > 192.168.80.2.5555
10.250.0.2.10011 > 192.168.80.2.5555
10.250.0.1.10001 > 192.168.80.2.5555
10.250.0.4.10031 > 192.168.80.2.5555
```

Therefore, `stats -s` and `stats -l` can count TX by PGID, but cannot assign RX packets back to the same PGID after decapsulation.

Conclusion

```text
TRex PGID is valid for TX offered load per slice.
TRex PGID is not valid for RX per slice after the BESS UPF decapsulates GTP-U.
```

For this reason, the current experiment uses a control-plane proxy.

## 🧮 Proxy model

The proxy estimates whether Gold had enough uplink capacity after the MBR-limited non-critical slices and hidden burst consumed part of the shared link.

The shared uplink capacity is currently

```text
200 Mbps
```

The traffic after MBR is

```python
after_mbr_gold   = min(offered_gold,   mbr_gold)
after_mbr_silver = min(offered_silver, mbr_silver)
after_mbr_bronze = min(offered_bronze, mbr_bronze)
after_mbr_hidden = min(hidden_burst,   mbr_noise)
```

Available capacity for Gold is

```python
available_for_gold = uplink_capacity - after_mbr_silver - after_mbr_bronze - after_mbr_hidden
```

Gold shortage is

```python
gold_shortage = max(0, after_mbr_gold - available_for_gold)
```

This is the main metric minimized by the DQN.

## 🎮 DQN action space

The online DQN chooses one of the following actions.

| Action ID | Action name | Gold MBR | Silver MBR | Bronze MBR | Meaning |
|---:|---|---:|---:|---:|---|
| 0 | `nominal` | 200000 | 100000 | 50000 | Initial nominal allocation |
| 1 | `cut_non_gold_light` | 200000 | 70000 | 30000 | Light cut on non-critical slices |
| 2 | `cut_non_gold_medium` | 200000 | 40000 | 15000 | Medium cut on non-critical slices |
| 3 | `cut_non_gold_strong` | 200000 | 15000 | 5000 | Strong cut on non-critical slices |
| 4 | `reserve_gold_light` | 220000 | 60000 | 20000 | Slight Gold reservation |
| 5 | `reserve_gold_strong` | 240000 | 15000 | 5000 | Strong Gold reservation |
| 6 | `restore_silver` | 220000 | 100000 | 10000 | Restore Silver, keep Bronze low |
| 7 | `restore_bronze` | 220000 | 30000 | 50000 | Restore Bronze, keep Silver low |

Noise is currently fixed at 50 Mbps MBR.

---

## 🎯 Reward function

The reward is a negative-cost objective.

The best behavior is reward close to zero.

A very negative reward means the policy caused Gold shortage or excessive poor allocation.

Current reward structure

```python
reward = (
    - 20.0 * gold_shortage
    - 0.35 * silver_mbr_drop
    - 0.20 * bronze_mbr_drop
    - 0.50 * action_change_penalty
    - 0.50 * non_gold_starvation_penalty
    +  5.0 * healthy_uplink_utilization
)
```

Interpretation

```text
reward very negative       bad policy
reward less negative       better policy
reward near zero           Gold protected with low penalty
```

This is normal for a cost-minimization RL setup. For presentation, a positive protection score can be computed later from the CSV.

```python
gold_protection_score = 1.0 - gold_shortage_mbps / offered_gold_mbps
```


### TRex complains about reused PG IDs

Clean both ports.

```bash
python3 - <<'PY'
from trex_stl_lib.api import STLClient

c = STLClient(server="127.0.0.1", sync_port=4501)
c.connect()
try:
    c.acquire(ports=[0, 1], force=True)
    c.stop(ports=[0, 1])
    c.reset(ports=[0, 1])
    c.clear_stats()
    print("TRex ports 0 and 1 cleaned")
finally:
    c.disconnect()
PY
```

### RX PGID stays zero

This is expected in this UPF decapsulation setup. Do not use RX PGID as the per-slice RX metric.

Use the proxy metrics instead.

### `tcpdump` on `enp8s0np0` shows zero packets

This can happen because TRex uses DPDK/PMD and packets do not pass through the Linux kernel path.

Use TRex counters or TRex capture instead.

### TRex capture on RX gets no packets

Enable service mode on RX port 1 before capture.

```text
service --port 1
```

## 🧪 Baseline 0, fixed MBR

The fixed baseline keeps the initial slice MBRs unchanged during the whole run.

```text
Gold    200 Mbps
Silver  100 Mbps
Bronze   50 Mbps
Noise    50 Mbps
```

This baseline represents a traditional static QoS configuration.

It answers the question

```text
What happens if the network operator configures slice MBRs once and never adapts them?
```

Expected behavior

```text
When Gold demand is low, this baseline can be acceptable.

When Gold demand rises, Silver, Bronze, and Noise can still consume part of the shared uplink.

Because the MBRs never change, the fixed baseline cannot reserve extra capacity for Gold before congestion occurs.

Therefore, Gold shortage can become high during Gold peaks or hidden burst periods.
```

Why it is fair

```text
It uses the same initial MBRs installed by the PFCP session setup.

It represents the simplest realistic operator policy.

It does not receive any learning advantage or future information.
```

Main limitation

```text
It cannot react to traffic variation.
```

---

## 🧪 Baseline 1, reactive threshold

The reactive baseline uses deterministic rules to select one of the same MBR actions available to the DQN.

It observes the current pressure and current Gold shortage, then reacts using thresholds.

Example behavior

```text
If Gold shortage is already visible, cut Silver and Bronze strongly.

If uplink pressure is high, cut Silver and Bronze moderately.

If Gold demand is low and pressure is low, restore non-critical slices.
```

This baseline answers the question

```text
Can a simple rule-based controller protect Gold without reinforcement learning?
```

Why it is stronger than fixed MBR

```text
It can change MBRs during the experiment.

It can reduce Silver and Bronze when the shared uplink is already under pressure.

It uses the same action space as the DQN.
```

Why it is still limited

```text
It is reactive, not predictive.

It usually acts after pressure or Gold shortage is already visible.

It does not learn the temporal pattern of Gold, Silver, Bronze, or hidden burst behavior.

It does not improve with experience.
```

Why it is fair

```text
It is simple, deterministic, and auditable.

It uses the same proxy measurements as the DQN.

It does not use hidden future information.

It provides a stronger comparison than fixed MBR.
```

## 🧠 Online DQN policy in the final comparison

The online DQN policy learns from interaction with the running testbed.

It uses normalized observations internally, while the original metrics remain saved in Mbps, kbps, reward, loss, pressure, and shortage for plotting and analysis.

The DQN chooses among the same MBR actions used by the reactive baseline.

Its advantage is that it can learn which actions tend to protect Gold under recurring traffic phases.

The DQN answers the question

```text
Can a learning controller anticipate the temporal demand pattern and reserve uplink capacity for Gold more effectively than fixed or reactive control?
```

Expected behavior

```text
When Gold demand is low, the DQN can allow more capacity for Silver and Bronze.

When Gold starts rising, the DQN can reduce Silver and Bronze before severe Gold shortage occurs.

When hidden burst pressure appears, the DQN can favor stronger non-Gold cuts.

Over time, the DQN should reduce Gold shortage and make reward less negative.
```

# Latent Space Ad-On

# Latent-Space Addon for QoS Slice Protection

A drop-in extension that adds a **UNUM-style predictive state-embedding** to an
existing reinforcement-learning experiment for protecting a critical network
slice over a shared uplink. This README is self-contained: even if you have
never seen the base experiment, you should finish it knowing exactly what the
addon does, how it is wired, and how to run it.

---

## 1. Background you need before the addon makes sense

The base experiment lives in
`~/Agentic-QoS-Sensing-through-Latent-Space/trex_4slice_noise_toolkit/`. Its
goal is to **protect a critical "Gold" traffic slice** over a shared 200 Mbps
uplink that also carries Silver, Bronze, and a hidden noise slice. Real
GTP-U traffic is generated by TRex, decapsulated and metered by a BESS-based
UPF, and a controller adjusts the per-slice **Maximum Bit Rate (MBR)** through
real PFCP `session modify` commands.

Because TRex's per-flow RX counters do not survive the UPF's GTP-U
decapsulation, the experiment uses a **deterministic proxy** for reward and
diagnostics: given the offered loads and the currently enforced MBRs, it
computes how much of the shared uplink remains available for Gold, and any
unmet Gold demand is recorded as `gold_shortage_mbps`. Minimizing this
shortage is the controller's job.

Three controllers were compared originally:

| Policy | What it does |
|---|---|
| **Fixed MBR** | Keeps the initial MBRs (200/100/50 Mbps) forever |
| **Reactive threshold** | Rule-based: cut Silver and Bronze when shortage or pressure crosses thresholds |
| **DQN (online)** | 8-action discrete DQN, trained online on the testbed, with an 11-dim observation: previous-step offered loads, a 1-step delta, the active MBR, and the previous step's pressure and shortage |

The DQN beats both baselines on Gold shortage. But its observation has the
exact weakness that the UNUM paper (NSDI'26, Chen et al.) flags for general
network controllers: **a few instantaneous and 1-step-difference signals are a
poor state estimate**. They cannot represent latent factors of the environment
(here: the on/off cycle of the hidden noise) and cannot anticipate the future.

The addon documented here adds a learned state representation that fixes that.

---

## 2. What the addon is, in one paragraph

A small but faithful adaptation of the UNUM idea to this testbed. It adds
(1) a **tokenizer + quantile bucketizer + encoder-decoder Transformer** that
produces a 16-dimensional **predictive embedding** of the recent network state
from a window of past observable signals; (2) a **pretraining pipeline** that
trains this embedder offline on diverse traffic and policies using
self-supervised *windowed next-token prediction*, then freezes it; (3) a
**unified online harness** that runs the original DQN, the baselines, or the
DQN over the frozen embedding — same environment, same reward, same action
space, same PFCP mechanism — so the only thing changing between conditions is
the state representation; (4) an **enriched environment** with richer latent
structure that better justifies the learned representation; and (5) a
**guardrail** that falls back to the reactive policy when the embedder's
predictions diverge from reality.

---

## 3. The UNUM principle, briefly

UNUM (Chen et al., *Unum: A New Framework for Network Control*, NSDI'26)
argues that today's network controllers — whether hand-engineered or learned —
under-perform because they use a thin notion of state: instantaneous values
and short running averages. UNUM proposes the **separation principle from
control theory** as the cure:

> An optimal feedback controller for a partially observed stochastic system
> can be decomposed into two distinct components: a **state observer** and a
> **deterministic controller**.

Concretely, UNUM:

1. **Tokenizes** raw network statistics over a control window.
2. **Discretizes** each feature with quantile-based bucketization, turning
   prediction from regression into classification.
3. **Pretrains** a Transformer encoder-decoder on diverse data with
   **windowed next-token prediction** (predict a window of *future* tokens
   from a window of past ones).
4. The encoder's output is the **embedding** the controller consumes.
5. The decoder's predictions feed a **guardrail** that disables the
   embedding-augmented controller if predictions go bad for long enough.

The embedder is trained **once, offline**, then frozen. Controllers see only
the embedding plus a few small anchors.

This addon follows that recipe.

---

## 4. What the addon adds, file by file

The addon consists of four Python modules in `scripts/` and one orchestrator
in the toolkit root.

### `scripts/traffic_model_enriched.py` — enriched environment

The original `sine_gold_safe_overload` environment has exactly two latent
factors: a binary noise on/off process and fixed sine phases. That is enough
to demonstrate that any controller beats a static baseline, but it is *too
easy* to justify a learned state estimator: anything with a tiny bit of
memory can track a 1-bit latent.

The enriched model adds three latent mechanisms with real temporal memory:

1. **3-state hidden noise Markov chain** (quiet → ramp → burst). Noise
   levels: 30 / 130 / 300 Mbps. Dwell times in seconds: quiet (90–180),
   ramp (15–35), burst (20–55). Transitions are biased so quiet always
   ramps before bursting, and bursts cool down through the ramp state most
   of the time. The agent never sees the noise; only its proxy
   consequence (pressure, shortage) is observable.

2. **Slowly drifting uplink capacity** (bounded AR(1) random walk).
   Base = 200 Mbps. Per-step innovation std = 1.5% of base, autoregression
   ρ = 0.97 (very slow). Capacity stays in [0.80, 1.10] × base. The burst
   state additionally costs 6% capacity (contention model). This is the
   "path-property latent" analogous to UNUM's wireless capacity changes.
   Invisible to the agent; threaded directly into the proxy so it affects
   `available_for_gold` and `gold_shortage`.

3. **Long-period Gold demand envelope** (sine of period ~600 s, ±25% on
   Gold's mean). This rewards a **longer observation context** — a short
   window cannot distinguish a slow Gold rise from a slow Gold fall.

The sample interface is a strict superset of the base `TrafficSample`. An
`EnrichedSample` carries the usual `step`, `t_s`, `regime`, `mbps` fields
plus `capacity_mbps` (used by the proxy for that step) and `hidden_state`
(audit-only, never an agent or embedder feature).

Two kinds are exposed: `latent_rich` (the default) and `latent_mild`
(gentler drift and noise for sanity runs).

### `scripts/unum_embedder.py` — the embedder

This module implements three things that travel together as a single
checkpoint.

**Token definition.** Seven observable features per step, fixed and shared
between pretraining and online inference (this is the single source of
truth and must not drift between the two):

```
1. offered_gold_mbps
2. offered_silver_mbps
3. offered_bronze_mbps
4. uplink_pressure
5. uplink_utilization
6. gold_shortage_mbps
7. available_for_gold_mbps
```

The hidden noise offered load and the latent capacity are **never** in the
token. The agent infers them through their consequences (pressure,
shortage) — exactly UNUM's latent-inference job.

**Quantile bucketizer.** Per-feature quantile boundaries, default 32
buckets per feature. Bucketization turns each token from a 7-vector of
floats into a 7-vector of integer bucket indices, and turns prediction
from regression into a classification problem. Boundaries are fit on the
pretraining corpus and stored inside the embedder checkpoint, so online
inference always uses the same bucketization seen during training.

**Transformer encoder-decoder.** A small but real architecture:

```
Per-feature bucket embeddings (each: nn.Embedding(n_buckets=32, dim=8))
    ↓ concat 7 features → 56-dim
Linear projection → d_model = 32
+ learned positional embedding (window length W=16)
    ↓
TransformerEncoderLayer × 2 layers
    nhead = 2, ff = 64, GELU, dropout = 0.1, CAUSAL mask
    ↓
Take output at the most recent position
Linear projection → embedding_dim = 16   ← this is what the controller sees
    ↓
H × D = 4 × 7 = 28 classification heads,
each predicting one (horizon_step, feature) bucket index from the embedding
```

The encoder is causal — at every position it attends only to past
positions — which matches the temporal nature of network state.

**Runtime.** `EmbedderRuntime` is what the online controller uses. It
holds the model and bucketizer, maintains a rolling 16-token window, and
exposes three operations:

- `push(observable_dict)` — append the latest completed-step observable.
- `embedding()` — return the current 16-dim latent (`torch.no_grad`,
  `model.eval`). Also caches the predicted next 4 tokens for the
  guardrail.
- `divergence(observed_dict)` — mean bucket-index distance between the
  previously predicted horizon-0 token and the now-observed token.

### `scripts/pretrain_embedder.py` — offline pretraining

Self-supervised, **no TRex required**. Runs entirely on CPU on any laptop.

The script:

1. **Collects** rollouts under diverse conditions. The default cross-product
   is 3 traffic models × 12 seeds × 3 collection policies = **108
   rollouts**. The 12 seeds are `0, 1, 2, 3, 4, 5, 8, 9, 10, 11, 14, 15`
   — deliberately disjoint from the evaluation seeds `7, 13, 21` so the
   embedder cannot memorize specific evaluation traces. The three
   collection policies are `random`, `reactive`, and `fixed`, giving
   cross-policy coverage of the proxy outputs (the same physical traffic
   produces different pressure/shortage signals under different MBRs).

2. **Fits the bucketizer** on the concatenated raw token stream.

3. **Builds training pairs** by sliding a window over each rollout: for
   every valid time `t`, the past 16 tokens form `X` and the next 4
   tokens form `Y`. No cross-sequence leakage (windows are built per
   rollout).

4. **Splits** 90% train / 10% validation.

5. **Trains** with `Adam(lr=1e-3)`, batch size 512, default 20 epochs.
   The loss is the **sum of cross-entropies over all 4 × 7 = 28
   (horizon, feature) heads**. Reported metrics: training loss,
   validation loss, and within-1 bucket accuracy (correct or one bucket
   off).

6. **Saves** the embedder checkpoint: model weights + bucketizer state +
   the EmbedderConfig + the list of OBS_FEATURES used at training. The
   list is checked on load so a stale embedder cannot be silently used
   with a modified feature set.

A `pretrain_log.csv` is written at the end with one row per epoch.

### `scripts/run_proxy_experiment.py` — unified online harness

A single script that can run every experimental condition through the same
code path. The only thing that changes between conditions is the policy
and the state representation. This is the key correctness property:
**identical environment, identical proxy, identical reward, identical
action space, identical PFCP mechanism** for all four conditions.

Flag combinations:

| `--policy` | `--obs-mode` | Equivalent to |
|---|---|---|
| `fixed_mbr` | (ignored) | the base `online_proxy_baseline.py --policy fixed_mbr` |
| `reactive_threshold` | (ignored) | the base `online_proxy_baseline.py --policy reactive_threshold` |
| `dqn` | `raw` | the base `online_dqn_proxy_train.py` (literally imports its `make_obs`) |
| `dqn` | `latent` | new — DQN over a frozen embedding + small anchors |

For `--obs-mode latent` the observation is:

```
obs = concat( embedding(16), active_mbr/300_000 (3), [prev_pressure, prev_shortage/200] (2) )  →  21 dims
```

The two anchors (`prev_pressure`, `prev_shortage`) and the active MBR are
exactly the same anchors used in the raw observation, so any improvement
is attributable to the embedding replacing the raw offered-load history.

Two environment options are exposed:

| `--env` | `--traffic-model` / `--enriched-kind` |
|---|---|
| `original` | one of `stochastic`, `sine_abrupt`, `sine_stress`, `sine_overload`, `sine_gold_safe_overload` (the base toolkit's existing models, fixed capacity) |
| `enriched` | one of `latent_rich`, `latent_mild` (the new model, time-varying capacity) |

In the enriched env each sample carries a per-step `capacity_mbps` that is
threaded into the proxy. In the original env the proxy uses the fixed
`--uplink-capacity-mbps` value. Same proxy function in both cases.

**Optional flags:**

- `--guardrail` enables the fallback (latent mode only).
  Parameters: `--guardrail-bucket-thresh 5.0`, `--guardrail-window 10`.
  When the embedder's mean bucket-index error stays above 5 for 10
  consecutive steps, the next action is taken from the reactive policy
  instead of the DQN. A `guardrail_active` column records each step.
- `--no-trex` skips TRex entirely — useful for smoke-testing the full
  pipeline on a laptop. Combine with `--no-apply` to also skip
  `pfcpctl`.

### `run_all_experiments.sh` — orchestrator

Driver that runs the entire comparison (pretrain → fixed → reactive →
vanilla DQN → latent DQN) for every seed in `${SEEDS}`. Designed for the
"Path B" enriched-environment comparison. Knobs are exposed as
environment variables so the same script does the smoke test and the
full run.

A separate, simpler `compare_single_abrupt_flow.sh` (in your repo, not in
the addon) handles "Path A": run only the latent DQN against the original
environment, on top of baselines and vanilla DQN you have already run.

---

## 5. Why this is the right experimental design

Three properties make this comparison clean.

**Apples-to-apples.** Every condition runs through the same proxy,
reward, action space, and PFCP machinery. The harness either imports
those pieces from your existing scripts or calls the same functions
directly. There is exactly one variable: the state representation.

**Separation of state estimation from control.** The embedder is trained
offline on a self-supervised objective that has nothing to do with the
reward. It is then frozen. The DQN learns online with replay and target
network, the same way it always did. This means any improvement is
attributable to the *representation*, not to a coupled training trick.

**No leakage of latent factors.** The hidden noise offered load and the
drifting capacity never appear in features for either the agent or the
embedder. They appear only through their observable consequences
(pressure, shortage, available-for-Gold). Inferring them is precisely
what the embedder is supposed to do.

## 9. CSV schema

`metrics.csv` is a **superset** of the base toolkit's schema. Existing
analysis scripts that read columns by name continue to work without
changes; the new columns are simply ignored unless you ask for them.

New columns added by the addon:

| Column | Meaning |
|---|---|
| `policy` | `fixed_mbr`, `reactive_threshold`, or `dqn` |
| `obs_mode` | `raw`, `latent`, or `n/a` (baselines) |
| `env` | `original` or `enriched` |
| `capacity_mbps` | per-step uplink capacity (enriched) or the CLI default (original) |
| `guardrail_active` | 1 if this step's action came from the reactive fallback, else 0 |
| `embedder_divergence` | mean bucket-index error between the previously predicted token and the observed token (NaN on the first step) |

Unchanged from base: every other column listed in
`online_dqn_proxy_train.py`'s fieldnames, including `gold_shortage_mbps`,
`uplink_pressure`, `reward`, `train_loss`, and the per-slice offered /
after-MBR / drop columns.

`episodes.csv` gains `policy` and `obs_mode` columns; everything else is
identical.

## 10. Reading the results

The headline measurement is **mean `gold_shortage_mbps` per policy**, with
a standard deviation across seeds. The qualitative ordering you expect:

```
Fixed MBR              worst Gold protection
    >
Reactive threshold     intermediate
    >
DQN vanilla            better in late episodes
    >
DQN latent             best, especially during noise bursts and
                       under low-capacity moments in the enriched env
```

Other useful angles:

- **Per-episode `gold_shortage_sum` and `reward_mean`** — learning curves.
  In the latent DQN you should see the curve cross the vanilla DQN's
  curve around the middle of training, then stay below it.
- **Action distribution per policy** — does the latent DQN reach for
  `cut_non_gold_strong` *before* the burst hits (anticipation), versus
  the vanilla DQN reacting after the fact?
- **`guardrail_active` rate** — should be low overall (a few percent). If
  it is very high, the embedder is too inaccurate and the latent
  controller is effectively the reactive baseline. Raise
  `--guardrail-bucket-thresh` or improve pretraining.
- **`embedder_divergence` over time** — should be small most of the
  time, with spikes near noise-state transitions. This is exactly the
  pattern that justifies the guardrail.
- **Stratify shortage by burst regime.** Split each step into "quiet"
  vs. "burst" using `hidden_burst_mbps` and compare per-policy shortage
  on each. The latent advantage should be much larger in the burst
  regime — that is where anticipation pays off.

The `pretrain_log.csv` is your sanity check on the embedder itself,
independent of the controller. Within-1-bucket accuracy in the 60–80%
range after 20 epochs is healthy for the default config. If it is below
40%, increase epochs, increase context window, or check the bucketizer.

## 11. Honest caveats

A short list of things that are easy to oversell if you are not careful.

**The latent factors in the original environment are low-dimensional.**
Binary noise on/off plus a fixed sine phase amounts to roughly one
informative bit of memory. A Transformer is sufficient but not
necessary; an LSTM or a small explicit HMM-style filter would probably
work too. The *architectural* claim of the addon — a separately trained
predictive state estimator feeding control — is what distinguishes it
from a plain DQN, not the specific choice of Transformer. The enriched
environment is what stresses that choice harder.

**Pure proxy mode is deterministic.** Given offered loads, MBRs, and
capacity, the proxy outputs are a closed-form function. The embedding
helps only because the noise load and the future offered loads are not
in the agent's features. State this explicitly when you report. The
DQN is not learning a noisy measurement model; it is learning to use a
representation that compresses temporal structure.

**Train/test seed discipline.** The pretraining seeds are disjoint from
the evaluation seeds by default. If you customize `PRETRAIN_SEEDS` or
`SEEDS`, keep them disjoint. Otherwise you are letting the embedder see
the exact trace it will be tested on, which inflates the result.

**The embedder is frozen during the online run.** This is deliberate
(separation principle) and is what makes attribution clean. Letting the
embedder continue to learn online is a reasonable next experiment but is
out of scope here.

**You will not see the latent advantage with bad pretraining.** If the
embedder's within-1-bucket accuracy is poor, the controller is reading
noise, and the guardrail will dominate. The headline number for the
latent DQN should always be reported alongside the embedder's
pretraining metrics so a reader can connect the two.

## 12. Quick troubleshooting

**"My run shows no `metrics.csv` after 30 minutes."** Confirm the
process is alive and consuming CPU (`ps -p <PID> -o %cpu,etime,cmd`).
If it is alive but the log file is empty, the Python stdout is
buffered — see the `python3 -u` note below. The metrics will still be
correct; only the live progress display is suppressed.

**"The log file is stuck at 22 bytes."** That is just the `nohup`
banner. The Python child is buffering stdout because it is not
attached to a terminal. For future runs, pass `python3 -u` in the
shell scripts:

```bash
sed -i 's/python3 scripts\//python3 -u scripts\//g' compare_single_abrupt_flow.sh
sed -i 's|python3 "\${SCRIPTS}/|python3 -u "\${SCRIPTS}/|g' run_all_experiments.sh
```

**"Loading the embedder errors with a feature-list mismatch."** The
embedder was trained against a different `OBS_FEATURES` than is
currently defined in `unum_embedder.py`. Either re-pretrain or restore
the matching feature list. Never edit a checkpoint by hand.

**"The DQN runs forever on the testbed without learning."** Check
`train_loss` in `metrics.csv`. It should be populated from step ~32
onward (after `warmup_steps`). If it is NaN throughout, the replay
buffer is not being sampled — most likely your `--batch-size` or
`--warmup-steps` is misconfigured relative to the run length.

**"The guardrail fires constantly."** The embedder is too inaccurate
for the chosen threshold. First, check `pretrain_log.csv` — if
within-1-bucket accuracy is below 0.5, pretrain longer. If pretraining
is healthy, raise `--guardrail-bucket-thresh` (default 5.0) to be more
permissive.

## 14. One-paragraph recap for someone in a hurry

Add four Python modules to the existing `scripts/` directory and one
shell script to the toolkit root. Pretrain a small Transformer once,
offline, on diverse traffic, to predict the next few steps of seven
observable network signals from a window of the past sixteen. Freeze
that Transformer. Run an online DQN whose state is the Transformer's
16-dimensional embedding plus a handful of anchor scalars, using exactly
the same proxy, reward, action space, and PFCP modify mechanism as
before. Compare it head-to-head against a static-MBR baseline, a
rule-based reactive baseline, and the original DQN that consumed only
instantaneous state. Optionally fall back to the reactive baseline when
the Transformer's predictions go wrong. The whole comparison is
orchestrated by a single shell script with three evaluation seeds; the
embedder uses a strictly disjoint set of training seeds. Results land in
a per-condition directory tree with a CSV schema that is a superset of
the original, so any analysis you wrote before keeps working.
